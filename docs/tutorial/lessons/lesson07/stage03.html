A. 本阶段核心心智模型（前置）

  1. 第一，Structured Output 的目标不是让模型输出“像 JSON 的文本”，而是得到 Parseable + SchemaValid + SemanticallyValid + PolicyValid 的可执行参数。
  2. 第二，合法 JSON 只解决语法层；JSON Schema 继续约束 Required、Type、Enum、Nested Object、Array 和是否允许额外字段，但 Schema 正确仍不代表业务语义正确。
  3. 第三，Semantic Validation 必须检查日期先后、金额范围、字段依赖、互斥条件和标识符一致性；Policy Validation 再决定这个结构化动作是否被授权。
  4. 第四，Constrained Generation 可以减少格式错误，但不能保证模型选对业务值；ConstrainedSyntax ≠ CorrectSemantics。
  5. 第五，Validation 失败后可以 Repair、Retry 或 Reject，但 Repair 只能用于确定性、无歧义的格式修复，绝不能为了让 Schema 通过而偷偷猜测缺失业务信息。

一、先锁死本阶段最重要的一句话

“能被人看懂”不是系统要求。

真正要求是：

Parseable+SchemaValid+SemanticallyValid+PolicyValid \boxed{ Parseable + SchemaValid + SemanticallyValid + PolicyValid }

也就是四层：

1. 能不能解析？
2. 结构对不对？
3. 值在业务上合理吗？
4. 这个动作是否允许？

因此：

LooksLikeJSON≠ExecutableArguments \boxed{ LooksLikeJSON \neq ExecutableArguments }

二、第一层：Syntax Validity——它首先必须真的是合法 JSON

合法 JSON 至少要求：

字符串使用双引号
没有多余尾逗号
对象和数组括号正确
布尔值是 true / false
null 使用标准写法
键名和字符串正确转义

例如：

{
  "query": "投标前本地机构限制",
  "jurisdiction": "广东省"
}

这是合法 JSON。

而：

{
  query: '投标前本地机构限制',
  jurisdiction: 广东省,
}

看起来像 JSON，

但严格来说：

不是合法 JSON。

因此第一道门是：

Parser

语法解析器

三、第二层：Schema Validity——合法 JSON 也可能完全不能用

假设工具定义要求：

{
  "query": "string",
  "jurisdiction": "string",
  "query_time": "YYYY-MM-DD"
}

模型输出：

{
  "query": "本地机构限制"
}

它是合法 JSON。

但缺少：

jurisdiction
query_time

如果这两个字段是必填，

它仍然不能执行。

所以：

ValidJSON≠ValidSchema \boxed{ ValidJSON \neq ValidSchema }

四、JSON Schema 到底解决什么？

JSON Schema 可以把“参数应该长什么样”写成机器可验证规则。

概念上：

{
  "type": "object",
  "properties": {
    "query": {
      "type": "string"
    },
    "jurisdiction": {
      "type": "string"
    },
    "query_time": {
      "type": "string"
    }
  },
  "required": [
    "query",
    "jurisdiction",
    "query_time"
  ]
}

它告诉 Runtime：

顶层必须是object
query必须是string
jurisdiction必须是string
query_time必须是string
三个字段都必须存在

所以：

Schema=MachineCheckableContract \boxed{ Schema = MachineCheckableContract }

五、Required Field：缺字段和字段为空不是一回事

假设：

jurisdiction

是必填字段。

这两个情况不一样：

情况 A：字段不存在

{
  "query": "本地机构限制"
}

情况 B：字段存在，但值为空

{
  "query": "本地机构限制",
  "jurisdiction": null
}

系统必须提前定义：

null 是否允许。

因此：

Required≠NonNull \boxed{ Required \neq NonNull }

很多 Agent Bug 就出在这里。

六、Type Constraint：类型不能靠猜

工具需要：

max_results = integer

模型却可能输出：

{
  "max_results": "10"
}

这里 "10" 是字符串，

不是整数。

有些 Runtime 会自动转成：

10

但这种自动类型转换必须非常谨慎。

因为：

"00123"

可能是：

项目编号的一部分，

而不是数字 123。

所以：

SilentTypeCoercion可能破坏业务语义 \boxed{ SilentTypeCoercion 可能破坏业务语义 }

高风险字段最好严格校验。

七、Enum：为什么受控字段不要让模型自由发挥？

假设采购阶段只能是：

pre_bid
evaluation
award
contract
acceptance

如果让模型自由生成，

它可能输出：

投标前阶段
招标前
前置阶段
before_bid

人能理解，

程序却很难稳定路由。

所以应使用：

Enum

枚举

概念上：

{
  "procurement_stage": {
    "type": "string",
    "enum": [
      "pre_bid",
      "evaluation",
      "award",
      "contract",
      "acceptance"
    ]
  }
}

这样输出空间从：

无限自然语言

收缩为：

有限合法状态集合。

八、additionalProperties：为什么“多生成几个字段”也可能是问题？

假设 Schema 只允许：

query
jurisdiction
query_time

模型却生成：

{
  "query": "本地机构限制",
  "jurisdiction": "广东省",
  "query_time": "2026-09-17",
  "legal_conclusion": "违法"
}

这里：

legal_conclusion

可能根本不应该出现在 Tool Arguments。

更危险的是：

模型提前把结论注入检索请求。

所以很多高可靠场景应该考虑：

additionalProperties = false

核心思想：

只允许Contract定义过的字段 \boxed{ 只允许Contract定义过的字段 }

九、Nested Object 和 Array：真实参数往往不是扁平字典

政府采购工具可能需要：

{
  "query": "资格条件审查",
  "filters": {
    "jurisdiction": "广东省",
    "valid_at": "2026-09-17"
  },
  "document_types": [
    "law",
    "regulation",
    "policy"
  ]
}

这里包含：

Nested Object
嵌套对象

Array
数组

复杂 Schema 的问题是：

约束更精确，

但模型生成难度也会上升。

所以设计原则不是：

Schema 越复杂越专业。

而是：

最小必要结构 \boxed{ 最小必要结构 }

只保留真正影响执行的字段。

十、第三层：Semantic Validation——Schema 对了，业务含义仍然可能错

这是 Structured Output 最容易被低估的一层。

例如：

{
  "effective_from": "2026-12-31",
  "effective_to": "2026-01-01"
}

两个字段都是合法日期字符串。

Schema 也完全通过。

但业务上：

effective_from>effective_to effective\_from > effective\_to

显然矛盾。

再比如：

{
  "min_amount": 1000000,
  "max_amount": 100000
}

类型都正确。

但范围不合理。

因此：

SchemaValid≠SemanticallyValid \boxed{ SchemaValid \neq SemanticallyValid }

这就需要：

Business Validator

业务语义校验器

十一、Semantic Validation 应该校验哪些东西？

政府采购 Tool Arguments 至少可能需要检查：

时间先后关系
金额上下限
辖区层级关系
文号格式
项目编号格式
采购阶段是否冲突
版本状态是否冲突
字段之间的依赖关系
互斥字段是否同时出现

例如：

如果 historical_query = true
那么 query_time 必须存在

或者：

如果 action = publish_notice
那么 approval_id 必须存在

这类规则：

不是 JSON Schema 的简单类型检查就能完全解决的。

十二、第四层：Policy Validation——结构和语义都正确，也不代表允许执行

假设模型输出：

{
  "action": "publish_notice",
  "project_id": "P_001",
  "content": "..."
}

它可能：

语法正确
Schema正确
业务字段正确

但用户当前权限只是：

read_only

那仍然必须拒绝。

所以完整校验链应该是：

Syntax→Schema→Semantics→Policy \boxed{ Syntax \rightarrow Schema \rightarrow Semantics \rightarrow Policy }

而不是：

JSON 能 parse 就直接执行。

十三、Constrained Generation：能不能让模型一开始就少犯格式错误？

可以。

一个重要思路是：

Constrained Generation

受约束生成

也就是：

在模型生成过程中，限制它只能生成符合某种结构的输出。

概念上：

普通生成：
任意Token都可能出现

受约束生成：
只允许当前Schema状态下合法的Token

这样可以大幅减少：

括号不闭合
字段名乱写
非法枚举值
多余自然语言

但必须注意：

ConstrainedSyntax≠CorrectSemantics \boxed{ ConstrainedSyntax \neq CorrectSemantics }

模型即使只能输出合法 JSON，

仍然可能选错：

jurisdiction
date
project_id
tool

十四、Validation 失败以后：Repair、Retry、Reject 三种策略

假设第一次输出：

{
  "query": "本地机构限制",
  "query_time": "明年"
}

Schema 要求：

YYYY-MM-DD

系统有三种典型处理方式。

1. Repair

修复

对于非常确定的格式问题，

Runtime 可以做安全修复。

例如：

去除多余空格
标准化大小写

但不能擅自把：

明年

猜成：

2027-01-01

因为这已经是：

语义推断。

2. Retry

重试生成

把 Validation Error 返回模型：

query_time必须为YYYY-MM-DD

让模型重新生成。

3. Reject

拒绝执行

如果问题高风险或无法安全修复：

不执行 Tool。

所以：

Repair只适合确定性、无歧义修复 \boxed{ Repair 只适合确定性、无歧义修复 }

十五、不要“自动补全”模型没有依据的信息

这是政府采购 Agent 非常重要的规则。

用户没有提供：

模型却输出：

{
  "jurisdiction": "广东省"
}

如果上下文根本没有广东省，

二十二、把本阶段压成最精准的 6 句话

第一，Structured Output 的目标不是让模型输出“像 JSON 的文本”，而是得到 Parseable + SchemaValid + SemanticallyValid + PolicyValid 的可执行参数。

第二，合法 JSON 只解决语法层；JSON Schema 继续约束 Required、Type、Enum、Nested Object、Array 和是否允许额外字段，但 Schema 正确仍不代表业务语义正确。
