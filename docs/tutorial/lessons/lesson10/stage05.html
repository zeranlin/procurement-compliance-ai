Batching：Static、Dynamic、Continuous Batching

A. 本阶段核心心智模型（前置）

  1. MaxBatch ≠ BestBatch。
  2. BatchSize ≠ TokenLoad。
  3. Continuous Batching 解决请求生命周期不同步。
  4. Prefill 与 Decode 会争 GPU，长 Prefill 会伤流式体验。
  5. HigherBatch 用 Queue / Tail Latency 换 Throughput。
  6. 100% Accept ≠ ReliableService，过载时需要准入控制。
  7. 生产配置应该找 Knee Point，不是绝对最大吞吐。

一、为什么 GPU 喜欢 Batch？

GPU 擅长并行。

如果每次只给一个小请求：

很多计算单元可能没有充分利用。

把多个请求组合：

A
B
C
D

可以提高：

Hardware Utilization

硬件利用率

所以：

Batching可以提高Throughput \boxed{ Batching 可以提高 Throughput }

二、Static Batching

固定收集 N 个请求：

凑满Batch
↓
一起执行
↓
等整批结束
↓
开始下一批

优点：

简单。

问题：

长度不同
输出时间不同
短请求被长请求拖住
新请求只能等下一批

所以：

SameBatch≠SameWork \boxed{ SameBatch \neq SameWork }

三、Batch Size 不等于计算量

请求：

A：100 input / 20 output
B：20000 input / 2000 output

数量都算 1，

但计算量完全不同。

所以：

BatchSize≠TokenLoad \boxed{ BatchSize \neq TokenLoad }

更需要关注：

batched tokens
active sequences
prefill tokens
decode tokens

四、Padding Waste

静态 Batch 中不同输入长度常需要补齐。

例如：

100
200
2000

如果按 2000 处理，

大量补齐部分没有真实信息。

所以：

Padding=PotentialComputeWaste \boxed{ Padding = PotentialComputeWaste }

五、Dynamic Batching

系统短暂等待，

把一小段时间内到达的请求组合起来。

收益：

吞吐提高。

代价：

等 Batch 本身产生 Queue Delay。

所以：

BatchWindow=ThroughputLatencyTradeoff \boxed{ BatchWindow = ThroughputLatencyTradeoff }

六、Continuous Batching

LLM 在线 Serving 更适合：

Continuous Batching

连续批处理

每个 Decode Step 之后：

完成请求
→ 退出

新请求
→ 加入

因此：

BatchMembership可以动态变化 \boxed{ BatchMembership 可以动态变化 }

它解决的是：

LLM 请求输出长度不同、生命周期不同步的问题。

七、核心心智模型 ①

Continuous Batching 不是“大 Batch”，而是“动态 Batch”

重点不是：

一次装更多。

而是：

请求可以动态加入和退出。

八、长 Prefill 会伤害 Decode

一个：

30000 Token Prefill

可能长时间占用 GPU。

已有流式请求：

等不到下一 Token。

这叫：

Decode Stall

解码卡顿

所以：

LongPrefill可能伤害ITL/TPOT \boxed{ LongPrefill 可能伤害 ITL / TPOT }

九、Chunked Prefill

把超长 Prefill：

分成多个小块。

在中间穿插 Decode。

所以：

ChunkedPrefill=PrefillDecodeSchedulingTool \boxed{ ChunkedPrefill = PrefillDecodeSchedulingTool }

十、核心心智模型 ②

Prefill 与 Decode 会争用同一套 GPU 资源

因此 Scheduler 必须决定：

谁先跑
每次跑多少
何时切换

这已经超出简单 Batch Size。

十一、Max Batched Tokens

比：

max_batch_size

更接近真实负载的是：

一次调度允许的总 Token 数。

因为：

ComputeLoad更接近TokenVolume \boxed{ ComputeLoad 更接近 TokenVolume }

十二、为什么更大 Batch 会伤 TTFT？

为了凑 Batch：

请求要等。

Batch 本身更重：

单轮时间也可能更长。

因此：

HigherBatch可能提高Throughput同时伤害TTFT \boxed{ HigherBatch 可能提高Throughput 同时伤害TTFT }

十三、Fairness 与 Priority

可以区分：

交互问答
高优先级

离线批量任务
低优先级

还要防止：

长请求饿死短请求
短请求永远抢占长请求

所以需要：

Fair Scheduling

公平调度

十四、Admission Control

系统接近饱和后，

继续无限接请求：

只会让 Queue 和 P99 爆炸。

所以可以：

限流
排队
拒绝
降级

因此：

100PercentAccept≠ReliableService \boxed{ 100PercentAccept \neq ReliableService }

十五、Knee Point

性能 Sweep 时会看到：

吞吐上升
↓
某一点之后
吞吐增长很少
但延迟急剧恶化

这个位置附近可以看作：

Knee Point

性能拐点

生产通常应该：

留在拐点之前，并保留 Headroom。

所以：

KneePoint比AbsoluteMaximum更有生产意义 \boxed{ KneePoint 比 AbsoluteMaximum 更有生产意义 }
