一、为什么自回归生成需要 KV Cache？

Transformer Attention 会为 Token 计算：

Query
Key
Value

生成第 tt 个 Token 时，需要关注前面的历史 Token。

如果每一步都重新计算所有历史 Token 的 Key / Value：

重复计算会非常大。

所以把历史的 K/V 缓存起来：

历史Token的K/V
→ 保存在显存

新Token
→ 只计算新增K/V

因此：

KVCache=MemoryForComputeTradeoff \boxed{ KVCache = MemoryForComputeTradeoff }

也就是：

用显存换掉重复计算。

二、KV Cache 显存怎样增长？

单个 Token 的 KV Cache 大致与：

2×Nlayers×Nkvheads×Dhead×Bytes 2 \times N_{layers} \times N_{kvheads} \times D_{head} \times Bytes

成正比。

前面的 2 表示：

K + V

序列长度 TT 增长时：

KVMemory∝T \boxed{ KVMemory\propto T }

并发序列 BB 增长时：

KVMemory∝B⋅T \boxed{ KVMemory\propto B\cdot T }

这不是所有实现的完整公式，

但抓住了最重要的工程关系：

Context Length 和活跃并发会直接推高 KV Cache。

三、MHA、GQA、MQA 与 KV Head

MHA 通常：

每个 Query Head 都对应独立 K/V Head。

GQA：

多个 Query Head 共享较少 KV Head。

MQA：

更大范围共享 KV Head。

所以：

FewerKVHeads⇒SmallerKVCache \boxed{ FewerKVHeads \Rightarrow SmallerKVCache }

因此参数量相近的模型：

推理 KV 成本也可能差很多。

五、Prefill 之后 Cache 已经开始占显存

输入：

10000 tokens

Prefill 会处理这些 Token，并为后续 Decode 建立 KV。

如果再输出：

2000 tokens

当前序列的 Cache 还会继续增长。

可以近似理解：

KVLength=InputTokens+GeneratedTokens \boxed{ KVLength = InputTokens + GeneratedTokens }

六、为什么长上下文 × 高并发特别危险？

一个请求从：

2K context
→ 32K context

KV 显存会显著增加。

再叠加：

Concurrency = 32

压力会继续放大。

所以：

LongContext×HighConcurrency=KVPressure \boxed{ LongContext \times HighConcurrency = KVPressure }

八、KV Cache Quantization

KV 也可以低精度保存。

降低动态 Cache 显存。

但这会近似 Attention 历史表示。

因此要测试：

关键Slice
不同Context Length
质量回归
真实性能

所以：

KVQuantization≠FreeMemory \boxed{ KVQuantization \neq FreeMemory }

九、Prefix Caching

如果很多请求共享：

System Prompt
公共政策前缀
相同RAG前缀

可以复用已经计算好的前缀 KV。

这叫：

Prefix Caching

前缀缓存

它主要节省：

重复 Prefill。

所以：

SharedPrefix→ReusableCompute \boxed{ SharedPrefix \rightarrow ReusableCompute }

十、核心心智模型 ③

Prefix Cache 是否有效，必须看 Hit Rate

如果命中率：

5%

实际收益可能很小。

如果：

70%

可能价值很高。

所以：

FeatureEnabled≠FeatureEffective \boxed{ FeatureEnabled \neq FeatureEffective }

十一、KV Cache 和 Batching 相互制约

并发更多：

GPU 更忙。

但活跃序列也更多：

KV Cache 更大。

所以：

BatchingGain受KVCapacity约束 \boxed{ BatchingGain 受 KVCapacity 约束 }

十二、Fragmentation

请求长度和结束时间不同，会不断申请、释放 KV 空间。

可能产生：

Fragmentation

内存碎片

即使总 Free VRAM 仍然存在，

也未必能找到合适的连续区域。

所以：

FreeVRAM≠AllocatableKV \boxed{ FreeVRAM \neq AllocatableKV }

下一阶段的 Paged Attention 就是为这种动态 KV 管理而生的重要思路。

十三、Eviction 与 Admission

Evict Cache
驱逐缓存

Recompute

Reject Request
拒绝新请求

所以系统需要：

Admission Policy

准入策略

决定：

当前容量还能不能安全接受更多请求。
