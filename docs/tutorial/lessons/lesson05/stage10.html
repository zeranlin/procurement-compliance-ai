答案是：

训练显存从来不只有 Model Weights。

真正的训练显存账本更接近：

Mpeak≈Mbase+Mtrainable+Mgrad+Moptimizer+Mactivation+Mtemporary+Mruntime \boxed{ M_{peak} \approx M_{base} + M_{trainable} + M_{grad} + M_{optimizer} + M_{activation} + M_{temporary} + M_{runtime} }

一、本阶段只解决一个核心问题

你以后碰到：

CUDA out of memory

第一反应不能再是：

“模型太大。”

而应该问：

到底是哪一类显存在涨？它主要跟 Parameter Count、Trainable Parameters、Sequence Length，还是 Micro Batch Size 有关？

二、今天只锁死 5 个核心心智模型

心智模型 1：Inference Memory ≠ Training Memory

推理时主要关心：

Model Weights
+
KV Cache
+
Activations / Runtime Buffers

训练时则需要：

Model Weights
+
Forward中间结果
+
Backward所需信息
+
Gradients
+
Optimizer States

所以同一个模型：

能推理，不代表能训练。

CanLoadForInference≠CanTrain \boxed{ CanLoadForInference \neq CanTrain }

心智模型 2：QLoRA 主要砍掉 Base Weight Memory，不会自动砍掉 Activation

第 9 阶段：

BF16 Base
约16-bit/parameter

变成：

NF4 Base
约4-bit/parameter + metadata

这对：

Base Weights

非常有效。

但 Forward 过程中每一层产生的：

Hidden States
Attention中间量
MLP中间量

并不会因为 Base Weight 是 4-bit：

全部自动缩成四分之一。

所以：

4bitWeights≠4bitActivations \boxed{ 4bitWeights \neq 4bitActivations }

心智模型 3：LoRA 让 Gradient / Optimizer 很小，但 Activation 仍经过完整 Base Model

QLoRA 中真正 Trainable 的：

LoRA A/B

很少。

因此：

Gradient Memory
Optimizer State Memory

相对 Full Fine-Tuning 可以小很多。

但一条 Token 仍然要跑过：

整个 Transformer。

所以：

7B Base
虽然Frozen

不等于：

Forward只算1%的模型

整个模型仍参与计算。

心智模型 4：Sequence Length 和 Micro Batch Size 是 Activation Memory 的两大旋钮

非常粗略地说：

Mactivation∝Bmicro×S×L×H M_{\text{activation}} \propto B_{\text{micro}} \times S \times L \times H

其中：

  • BmicroB_{\text{micro}}：单次真正送进 GPU 的样本数；
  • SS：Sequence Length；
  • LL：Transformer 层数；
  • HH：Hidden Size。

真实公式会复杂得多，但这个心智模型非常有用。

也就是说：

参数没变，只把 2048 Token 改成 8192 Token，训练显存也可能完全变成另一回事。

心智模型 5：OOM 要按“显存来源”诊断，不能随机调参

最差的调试方式：

OOM
↓
rank乱改
↓
batch乱改
↓
alpha乱改
↓
再装几个包

正确思路：

OOM
 ↓
是哪类Memory？
 ↓

 ↓
只改最相关的旋钮
 ↓
重新测Peak VRAM

这叫：

Memory Attribution

显存归因

三、训练显存正式拆成 7 个账户

显存账户 主要由什么决定 QLoRA 是否明显降低
Base Weights Base 参数量、量化位宽 是，核心收益
LoRA / Trainable Weights Rank、Target Modules 数量本来就小
Gradients Trainable 参数量 LoRA 大幅降低
Optimizer States Trainable 参数量、优化器 LoRA 大幅降低
Activations Batch、Sequence、模型结构 不会自动消失
Temporary Buffers Attention/kernel/算子 部分受实现影响
Runtime Overhead CUDA、allocator、框架等 与4-bit不是一回事

以后看到显存：

就用这 7 个账户查账。

四、账户 1：Base Model Weights

这是最好理解的一块。

如果模型有：

N N

个参数。

BF16 理论裸权重：

Mbase≈2N bytes M_{\text{base}} \approx 2N \text{ bytes}

7B：

7×109×2≈14GB 7\times10^9\times2 \approx14GB

QLoRA 4-bit 裸编码理论上：

7×109×0.5≈3.5GB 7\times10^9\times0.5 \approx3.5GB

但上一阶段已经强调：

实际驻留显存还要加量化 Scale、Metadata、非量化参数、临时工作区等。

因此这里最重要的不是死记：

7B = X GB

而是：

BaseWeightMemory∝ParameterCount×StorageBits \boxed{ BaseWeightMemory \propto ParameterCount \times StorageBits }

这块就是 QLoRA 最擅长压缩的地方。

五、账户 2～4：LoRA Weight、Gradient、Optimizer State

假设 LoRA 真正可训练参数只有：

20M Parameters

那么需要 Gradient 的：

主要也是这 20M。

Optimizer 需要保存状态的：

主要也是这些 Trainable Parameters。

这和 Full Fine-Tuning 完全不同。

Full FT：

7B参数
都可能需要Gradient和Optimizer State

LoRA：

7B Base
Frozen

20M LoRA
Trainable

所以：

OptimizerMemory主要跟TrainableParameterCount走 \boxed{ OptimizerMemory 主要跟 TrainableParameterCount 走 }

而不是简单跟：

Base Model 总参数量走。

六、为什么 Optimizer State 有时比你想象得更贵？

例如常见 AdamW 会为可训练参数维护：

First Moment
m

Second Moment
v

这些状态可能使用 FP32 等精度。

某些训练方案还可能存在：

Master Weights

等额外副本。

因此不能机械记：

“一个参数训练永远固定 X bytes。”

因为这取决于：

Optimizer
Parameter Dtype
Gradient Dtype
Mixed Precision实现
8-bit Optimizer与否
Framework

长期正确心智模型：

OptimizerState跟TrainableParameters强相关 \boxed{ OptimizerState 跟 Trainable Parameters 强相关 }

这正是 LoRA 为什么能省大量训练显存。

七、真正的大户：Activations

这里就是很多人第一次 QLoRA OOM 的原因。

假设输入经过第 1 层 Transformer：

Hidden State
↓
Attention
↓
MLP
↓
Layer Output

然后还有：

第2层
第3层
...
第32层

Backward 要计算：

每一步参数变化对最终 Loss 的影响。

因此训练期间需要保存或能够重新得到大量中间信息。

这些中间结果统称：

Activations

激活值 / 中间激活

可以把它理解成：

Forward 为了让 Backward 以后能够追责，留下的计算现场。

八、为什么 Batch Size 会直接推高 Activation？

假设：

micro_batch_size = 1

GPU 同时保存：

一条 Sequence 的大量中间结果。

改成：

micro_batch_size = 4

现在同一时刻要处理：

4 条。

因此很多 Activation Memory 会近似跟：

Bmicro B_{\text{micro}}

一起增加。

注意我这里特意写：

Micro Batch Size

而不是：

Effective Batch Size

这两个后面必须分开。

九、为什么 Sequence Length 更危险？

假设：

Batch = 1

但长度：

2048
→
4096
→
8192

每层都要处理更多 Token。

大量 Hidden State 相关存储大致会随：

S S

增长。

Attention 又更特殊。

经典 Attention 计算里：

QKT QK^T

会形成与：

S×S S\times S

相关的结构。

因此传统实现的某些 Attention 中间内存：

O(S2) O(S^2)

增长非常快。

这就是为什么：

长上下文训练特别容易吃显存。

十、但这里必须做一个现代实现修正：FlashAttention 会改变“显存复杂度”，不会改变所有计算规律

如果使用传统 Attention，并显式保存完整 Attention Matrix：

S2S^2 中间结果会非常昂贵。

FlashAttention / 高效 SDPA 等实现：

不需要把完整 Attention Matrix 长时间写回显存。

因此能显著降低 Attention 的峰值显存。

所以不能简单说：

“序列长度翻倍，所有训练显存一定四倍。”

这是不精确的。

更准确：

Attention 的理论计算量依然随序列长度呈近似二次增长，而高效 Attention Kernel 可以避免完整 S2S^2 Attention Matrix 的显存驻留，使实际峰值显存增长比朴素实现健康很多。

这条区别很重要：

ComputeComplexity≠StoredActivationMemory \boxed{ ComputeComplexity \neq StoredActivationMemory }

十一、Gradient Checkpointing 为什么能省显存？

正常做法：

Forward
↓
保存大量Activation
↓
Backward直接使用

Gradient Checkpointing：

梯度检查点

采用：

Forward
↓
只保留部分Checkpoint
↓
其他Activation不长期保存
↓
Backward需要时
重新Forward计算

也就是：

Memory↓换取Compute↑ \boxed{ Memory \downarrow \quad \text{换取} \quad Compute \uparrow }

中文：

不存那么多计算现场，等需要的时候再重算。

十二、Gradient Checkpointing 省的不是 Model Weight

这一点很容易搞混。

QLoRA：

主要压 Base Weight。

Gradient Checkpointing：

主要压 Activation。

所以二者非常互补：

QLoRA
        ↓
Base Weight Memory ↓

Gradient Checkpointing
        ↓
Activation Memory ↓

这也是为什么这两个技术经常一起出现。

十三、Gradient Accumulation 又是在解决什么？

假设你希望：

Effective Batch Size = 16

但 GPU 一次只能放：

Micro Batch Size = 2

可以让 8 个 Micro-batch：

forward
backward

forward
backward

...

累计8次Gradient

然后：

optimizer.step()

于是：

Beffective=Bmicro×GradientAccumulationSteps B_{\text{effective}} = B_{\text{micro}} \times GradientAccumulationSteps

单卡、单进程的简化情况例如：

2×8=16 2\times8=16

这叫：

Gradient Accumulation

梯度累积

十四、Gradient Accumulation 最容易被误解的一点

它可以让：

有效 Batch 变大，而不要求一次把整个 Batch 放进 GPU。

但是：

GradientAccumulation不会让单个MicroBatch本身变小 \boxed{ GradientAccumulation 不会让单个MicroBatch本身变小 }

所以如果：

micro_batch = 1
sequence_length = 32K

这一条本身已经 OOM，

再把：

gradient_accumulation_steps

从 4 调到 32：

没用。

因为连第一条 Forward 都进不去。

十五、Packing 对显存又是什么关系？

第 4 阶段学了 Packing。

Packing 的主要目标是：

Token Utilization

减少 Padding Waste。

但一定不要误解成：

packing=True 必然降低 Peak VRAM。

如果 Packed Sequence 最终仍是：

4096 Tokens

GPU 依然需要处理：

一条 4096 长度 Sequence。

Packing 的主要收益更接近：

同样的计算长度中，装更多真实训练 Token。

它是：

Efficiency Optimization

而不一定是：

Peak Memory Reduction

这一点很关键。

十六、为什么 Rank 通常不是 QLoRA OOM 的第一嫌疑人？

假设：

r = 16

改成：

r = 8

LoRA Trainable Parameters 的确减少。

Gradient 和 Optimizer State：

也会减少。

但如果真正显存大头已经变成：

Activations

那么这个变化：

可能救不了多少显存。

所以出现 OOM 时，不要机械：

先砍Rank

要看账本。

对于 QLoRA，一个很常见的优先诊断方向反而是：

Sequence Length

Gradient Checkpointing

Attention Implementation

十七、7B QLoRA 为什么“模型才几 GB”仍然会 OOM？

假设只是概念例子：

十八、还有一个经常混进来的东西：KV Cache

推理阶段我们经常讨论：

它会随着生成长度和 Batch 增长。

但普通 Causal LM 训练时：

通常并不需要像自回归推理那样保留跨生成步骤的 KV Cache。

所以看到训练 OOM：

不要第一时间把所有显存都归因到推理阶段熟悉的 KV Cache。

训练真正的大头通常另有其人。

二十三、把本阶段压成最精准的 5 句话

第一，训练显存不只是模型权重，而是 Base Weight、Trainable Weight、Gradient、Optimizer State、Activation、Temporary Buffer 和 Runtime Overhead 的总和。

第二，QLoRA 主要降低冻结 Base Model 的 Weight Memory，LoRA 主要降低 Gradient 和 Optimizer 对应的 Trainable Parameter Memory，但完整 Transformer 的 Activation 仍然存在。

第三，Micro Batch Size 和 Sequence Length 是 Activation 显存的核心变量；长上下文尤其昂贵，高效 Attention 可以降低中间显存，但不会让长序列计算免费。

第四，Gradient Checkpointing 用额外计算换 Activation 显存；Gradient Accumulation 用多个小 Micro-batch 组成较大的 Effective Batch，两者解决的是完全不同的问题。

第五，OOM 不是“模型太大”四个字能解释的；必须先定位显存账户，再调对应变量，并用真实 Peak VRAM 验证。
